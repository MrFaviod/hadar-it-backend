# Internationalization (SDK v2)

An extension can ship its own translations, and a **language pack** can add a
new language or fill/override existing text without touching core code. Both use
one catalog format: a flat JSON object of dotted keys to strings.

```json
{"ext.software-licenses.title": "Licencias", "api.error.not_found": "Não encontrado."}
```

Named parameters use `{name}`. Plural forms are separated by ` | ` in CLDR
category order for the locale and are selected by the `count` parameter, so a
translation must keep the same parameter names and the same number of plural
forms as its source text.

## Namespaces

| Prefix | Owner |
| --- | --- |
| `ui.*` | the frontend |
| `api.*` | the backend core catalogs |
| `ext.<extensionId>.*` | the module with exactly that id |

A module may only define `ext.<its own id>.*`. A key in another namespace, or a
repeated key inside its own namespace with a different meaning, is a validation
error. Replacing an existing translation is only possible from a language pack
and only by listing the key in its `overrides`; a silent replacement is
rejected with storage unchanged.

## Optional `i18n` block (ordinary extensions)

```json
{
  "i18n": {
    "sourceLocale": "es",
    "catalogs": {"es": "i18n/es.json", "en": "i18n/en.json"}
  }
}
```

- `sourceLocale` must be one of the declared catalogs; it is the reference for
  parameter and plural-form parity.
- Every non-source catalog must define exactly the source keys with matching
  parameters and plural forms.
- Catalog and doc paths must live under `i18n/` in the archive and end in
  `.json` (catalogs) or `.md` (docs). Undeclared `i18n/` files are rejected.
- `i18n.overrides` is not allowed; an extension's block cannot replace text it
  does not own. Use a language pack.
- Installing a module registers its catalogs as an owner provider; upgrading
  replaces them atomically and bumps the catalog revision; uninstalling removes
  them. A module without an `i18n` block contributes nothing.

## Language pack kind

A language pack is a normal SDK package with `"kind": "language-pack"` instead
of a runtime. It carries no `backend.py`, `frontend.js`, permissions,
operations, collections or storage, and **no code is ever executed**.

```json
{
  "sdkVersion": 2,
  "kind": "language-pack",
  "id": "pt-br",
  "name": "Português (Brasil)",
  "version": "1.0.0",
  "locales": [{"tag": "pt-BR", "name": "Portuguese (Brazil)", "nativeName": "Português (Brasil)"}],
  "compatibility": {"core": "^0.1.0", "extensions": {"software-licenses": "^1.0.0"}},
  "catalogs": {"pt-BR": "i18n/pt-BR.json"},
  "overrides": [],
  "priority": 10,
  "docs": {"pt-BR": {"licenses": "i18n/docs/pt-BR/licenses.md"}},
  "review": {"status": "draft"}
}
```

| Field | Rule |
| --- | --- |
| `id` | Same id rules as an extension; it identifies the provider. |
| `name` | Display name of the pack, at most 120 characters. |
| `version` | Strict `X.Y.Z`; an update must be newer than the installed version. |
| `locales` | One or more `{tag, name, nativeName}`; tags are canonicalized (`pt-BR`, `pt-br` are the same locale) and must be unique. |
| `compatibility` | `core` is required; `extensions` maps installed module ids to ranges. |
| `catalogs` | Locale → `i18n/**/*.json`; every declared locale needs a catalog. |
| `overrides` | Keys this pack replaces on purpose. `[]` means fill-only. |
| `priority` | `0..1000`; among overriding packs the higher priority wins, then the lexicographically greater pack id. |
| `docs` | Locale → `{topic: "i18n/docs/.../*.md"}`; topics must be non-empty files. |
| `review.status` | `draft` or `reviewed`. |

Compatibility ranges accept `*`, an exact `X.Y.Z`, and `~X.Y.Z`, `^X.Y.Z`,
`>`, `>=`, `<`, `<=` prefixes. A pack whose core range does not match the
installed core, or whose named extension is missing or outside its range, is
refused at approval.

## Install, review, update, uninstall

1. `POST /api/v1/extensions/candidates` with the archive. Admission parses the
   catalogs, checks namespaces, source parity and declared files. A language
   pack needs no validator container report: there is no code to execute.
2. `POST /api/v1/extensions/candidates/{id}/approve` installs it. At this point
   the host also checks compatibility and owner conflicts against the database.
3. `POST /api/v1/extensions/{id}/review` with
   `{"status": "draft"|"reviewed", "expectedVersion": <module revision>}`
   requires the caller's `system.modules` permission and a persisted human
   Superadmin. A `draft` pack is installed but inactive; reviewing it
   `reviewed` publishes its catalogs, and a revision bump invalidates cached
   bundles.
4. Approving a newer version replaces the provider atomically.
5. `POST /api/v1/extensions/{id}/uninstall` deletes the provider. Earlier
   owner and pack translations come back on the next snapshot; owner catalogs
   are never modified by a pack.

Agents may build packs; keep `review.status` at `draft` so a human publishes the
text. The unpacked layout is `extension.json`, `i18n/<locale>.json` and
`i18n/docs/<locale>/<topic>.md` — nothing else.

See `templates/` for bilingual module catalogs and
`examples/language-pack-pt-br/` for a validated pt-BR pack.
